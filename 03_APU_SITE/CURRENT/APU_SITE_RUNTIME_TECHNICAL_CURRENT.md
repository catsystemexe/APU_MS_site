## B1.6-A runtime observability (2026-10-14)

Implemented in `5e08e670bfb65fab58606e805d47cfed44fb3a87` on the F1–F3 stabilization branch; this entry completes the canonical documentation for that implementation.

- Optional `telemetry.grounding` records separate `primary` and `rescue` attempts. Each includes handling `status` (`completed`, `failed`, `skipped`), `call_id`, wall-clock `duration_ms`, configured `model`, canonical `provider_status` / `application_status`, safe `failure_reason` / `skipped_reason`, and per-attempt `usage`. Usage retains input, cached-input, cache-write, output, reasoning and provider-total token values; unavailable values remain null. A skipped attempt has no invented call ID, duration or usage. Call IDs associate attempted grounding with the existing canonical usage/pricing records, without altering those records.
- Grounding failure reasons distinguish provider failure, incomplete response, transport failure, JSON parse failure, missing structured output, grounding contract validation failure and unknown failure. Skip reasons are `no_candidates`, `primary_failed` and `no_explicit_rejections`. Attempt handling status is distinct from provider/application status: for example, a completed provider call whose parsed object lacks the required verdict array can still fail subsequent grounding handling while retaining its original canonical accounting status.
- `grounding.counts` contains `submitted`, `primary_accepted`, `primary_explicit_rejected`, `primary_unresolved`, `rescue_submitted`, `rescue_accepted` and `final_accepted`. Counts concern the normalized add/conflict candidates requiring grounding, not duplicate/skip records. `primary_unresolved` counts candidates in neither the primary acceptance set nor the unambiguous explicit-rejection set, including missing or ambiguous verdicts. Rescue acceptance counts only candidates added to the primary acceptance set. Failed primary calls do not create rescue eligibility; failed or invalid rescue retains primary acceptances. Partial/contradictory primary verdict handling and the existing strict, atomic rescue validation remain unchanged.
- The existing aggregate `stages` row named `grounding` remains intact, with its combined timing/usage and legacy status semantics. It is a compatibility summary, not proof that both attempts succeeded; use the new per-attempt fields to identify failure or skipping. Existing stage names, paths and summary aggregation are preserved.
- Optional `telemetry.controller.rejection_reason` identifies the first failed existing validation check, such as phase mismatch, invalid action shape/order, NAV option mismatch, repeated SIDE target or an already answered category. The existing `controller.mode` and coarse `fallback_reason` remain. Detailed rejection is null for successful validation and for provider/transport/JSON failures that never reach contract validation. Codes are allowlisted identifiers, not question text, prompts, generated output or raw exception/provider messages. Existing NAV, pending SIDE, phase/readiness and fallback decisions are unchanged.
- Session JSON remains schema **1.0**. `grounding` and `controller.rejection_reason` are optional, additive fields retained through telemetry merge/export; older telemetry without them remains valid. New details are emitted only in developer-gated route telemetry and are available through the existing developer Session JSON export. Normal-user extraction contracts, existing role-independent canonical usage collection and inline Chat diagnostic visibility are unchanged.
- Observability adds no provider calls, retries or deterministic bypass expansion. F1 acceptance/rejection decisions, rescue eligibility, Core, prompts, models, reasoning and service-tier configuration are unchanged.
